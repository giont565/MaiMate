## 決策 1｜Golden Path 與「不下單」原則怎麼共存
**誰決定：你 ＋ 後端（A 包）** ｜ **最緊急，會影響決賽腳本**

規格 §11 說「本次不要實作下單」，但 README 的決賽 90 秒主線就是下單流程，且它就住在 Screen 7。

| 選項 | 做法 | 代價 |
|---|---|---|
| **A（建議）｜共存，改規格措辭** | Screen 7 同時支援「分析對話」與「Golden Path 下單確認流程」。把 §11 改寫成：**AI 不得自行執行交易；下單只能由使用者在確認卡上親自確認，確認卡由後端 `prepare_order` 產生**。 | 幾乎零成本——現況本來就是這樣（`execute_order` 對 LLM 隔離）。只需改規格文字。 |
| B｜分頁：對話頁不含下單，另留舊頁跑 Golden Path | Screen 7 純分析；下單另走現在的 `index.html`。 | 評審會看到兩套設計語言；導覽變複雜；README 的主線變成「另一頁」，簡報不好講。 |
| C｜照規格拿掉下單 | Screen 7 完全不含下單。 | **決賽 Golden Path 沒有舞台**，等同放棄 README 主線分數。不建議。 |

**建議 A。** 理由：規格真正要禁的是「AI 自動下單」，而不是「使用者親手確認」；兩者從來沒有真的衝突，是措辭問題。

## 決策 2｜`navigation_context` 要不要進後端契約
**誰決定：後端（A 包）為主**

前端 `app.js:322` 已經在送，但 README §3 契約與 `chat.py` 都沒有它 → 來源脈絡目前**整包被丟掉**。

| 選項 | 做法 | 代價 |
|---|---|---|
| **A（建議）｜進契約，最小欄位** | 後端接收 `{sourceModuleId, sourceInsightId, sourceQuestionId, marketContextId}`（**只收 ID，不收數字與文字**），放進 system prompt 或工具參數。 | 後端小改（parse + 塞 prompt）。前端零改動（已在送）。 |
| B｜不進契約，前端自己把脈絡寫進問題文字 | 例如送出「（承接：今天，什麼和你有關？）為什麼 BTC…」。 | 立刻可用、不必等後端；但脈絡變成使用者可見的雜訊，且無法驗證來源真偽。 |
| C｜維持現狀（送了但沒人接） | — | **來源卡變成純裝飾**，規格 §5「Context 由後端重新讀取」直接做不到。不建議。 |

**建議 A；若後端沒空，退而求其次選 B**（至少脈絡真的有作用），並在規格標明這是暫時做法。

## 決策 3｜Streaming 要不要真做
**誰決定：後端（A 包）**

`/chat` 現在是一次性 JSON（`chat.py:42`），規格要 SSE ＋ 9 種事件 ＋ 可取消。

| 選項 | 做法 | 代價 |
|---|---|---|
| **A（建議）｜Mock 端模擬串流，正式端維持整段** | 前端 Service 介面照規格定（含 cancel），Mock 實作逐段吐字；正式端先顯示「麥麥正在整理…」＋工具狀態，回來就整段呈現。 | 決賽 demo 看得到串流效果（跑 mock），且不必等後端。介面已備好，之後後端加 SSE 直接換實作。 |
| B｜請後端加 SSE | 真串流。 | 要問 A 包時間成本；Lambda + API Gateway 的 SSE 要額外設定，決賽前風險偏高。 |
| C｜前端做假的打字動畫（正式端也假裝逐字） | 視覺一致。 | **等於騙評審**，違反我們的誠實原則。不建議。 |

**建議 A。**

## 決策 4｜Analytics 事件參數要不要放寬
**誰決定：你**

現行 `mm_events` 只准 `{e}` 或 `{e,q}`，**四支煙測硬鎖**（`smoke_onboarding:204`、`smoke_analysis:554`、`smoke_home:239,578`、`smoke_welcome:128`）。規格 §29 想要 7 個參數。

| 選項 | 做法 | 代價 |
|---|---|---|
| **A（建議）｜放寬成列舉值白名單** | 允許 `{e, q, src, intent, tool, style, status, guard}`，**每個欄位只准列舉值**（禁自由文字、禁任何金融數字、禁 ID 以外的識別資訊），並在煙測加「值必須在列舉集合內」的斷言。 | 要改四支煙測（約 20 分鐘）。隱私上仍守得住：沒有問題原文、沒有金額、沒有持倉。 |
| B｜維持 `{e,q}`，把分類編進 `q` | 例如 `q: "intent_recommendation"`。 | 零改動，但語意擠在一個欄位、之後難分析。 |
| C｜照規格全開 | 含 `evidenceCount` 等數值。 | 數值欄位會逐漸長成「可反推個人資料」的破口。不建議。 |

**建議 A。** 這是唯一需要你點頭鬆綁隱私約束的地方，所以特別標出來。

## 決策 5｜對話紀錄怎麼保存
**誰決定：你**

規格 §25 要歷史清單；但 Screen 6 現行原則是「完整回覆只存 30 分鐘同分頁 sessionStorage，不長期寫 localStorage」（因為回覆含個人化數字）。

| 選項 | 做法 | 代價 |
|---|---|---|
| **A（建議）｜清單長存、內容短存** | localStorage 只存「標題＋來源標籤＋時間＋是否用個人資料」；訊息內容放 sessionStorage（30 分鐘 TTL）。過期後點進去顯示規格 §28 本來就有的「這段展示對話已過期」。 | 與 Screen 6 原則一致；決賽現場同一分頁不會過期，demo 不受影響。 |
| B｜全部長存 localStorage | 重開瀏覽器仍可看完整對話。 | 個人化數字長期落在瀏覽器；與 Screen 6 原則不一致，審查會再抓一次。 |
| C｜全部只存 sessionStorage | 最保守。 | 關掉分頁連清單都沒了，規格 §25 的歷史清單形同虛設。 |

**建議 A。**

## 全部照建議走的話，結論長這樣

1. Golden Path 與分析對話**共存**，改規格措辭（AI 不自行下單，使用者親手確認）
2. `navigation_context` **進後端契約**（只收 ID）；後端沒空則暫時走文字承接
3. Streaming **Mock 端模擬、正式端整段**，介面照規格留好
4. Analytics **放寬成列舉值白名單**，同步更新四支煙測
5. 對話紀錄**清單長存、內容 30 分鐘**
6. Demo 數字**改規格文字對齊 mock**（52%／72%／1 筆／0.7 筆／1 月）
7. 紅綠：對話區不用、Golden Path 保留；工具名：加人話對照表

其中 **2 與 3 需要後端點頭**，其餘四項你自己就能定。
