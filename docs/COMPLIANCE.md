> **本文是工程自查，不是法律意見。** 虛擬資產服務法立法中，商業化前必須過正式法遵。
> 寫作原則：**每一條合規主張都要指得出程式碼**。指不出來的，就誠實寫在 §5「還沒做到的」，
> 不用漂亮話蓋過去。

## 0. 立場

金融 AI 產品最常見的合規做法是**寫一段免責聲明**，然後照做原本想做的事。

MaiMate 的作法相反：**先問「這件事我們能不能在架構上做不到」**，做得到就從系統裡拿掉，
拿不掉才用提示詞與正則去攔。

差別在哪：免責聲明保護的是公司，架構限制保護的是使用者。前者出事時說「我們有講過」，
後者是「那件事我們的系統根本執行不了」。

以下每一節都照這個順序寫：**架構上做不到的 → 程式攔的 → 只能靠告知的**。

---

## 1. 不代操：AI 沒有下單的能力

### 主張
使用者說「幫我賣掉」，MaiMate **不會、也不能**替他下單。

### 架構證據（不是提示詞，是能力缺失）

| 事實 | 位置 |
|---|---|
| 真實下單函式 `execute_order` 存在 | `backend/agent/tools.py:241-247` |
| 但**不在** LLM 的工具清單 `TOOLS` | `tools.py:21-105` |
| 也**不在**執行分派表 `_DISPATCH` | `tools.py:250-259` |
| 唯一真正送單的路徑，在另一支 Lambda | `backend/handlers/order.py:56` |
| 該檔註解明訂此紅線 | `order.py:12`、`tools.py:3-6, 242` |

模型在推論時**看不到**這個工具的定義，因此不會產生呼叫它的意圖；就算幻覺出這個名字，
分派表裡也沒有對應項目，不會有任何東西被執行。

### 為什麼這比「提示詞禁止」強

提示詞是請求，模型可能不照做（越獄、長對話漂移、多語言繞過都是已知手法）。
把函式從清單裡移除，模型照不照做就無關緊要了——**它沒有那個能力**。

### 人在迴圈中

| 機制 | 位置 | 數值 |
|---|---|---|
| 確認憑證有效期 | `tools.py:19` | `CONFIRM_TTL_SEC = 60` 秒 |
| 憑證產生（只產卡，不下單） | `tools.py:220-238` | 回傳 `confirm_token` + `ttl_seconds` |
| 過期檢查 | `order.py:25, 29` | — |
| 過期回應 | `order.py:51-53` | HTTP **410** |

即使有人拿到憑證，60 秒後它自己失效。**每一筆都要人重新按一次**，沒有「授權一次、之後自動」。

## 2. 不報明牌：四層攔截

### 主張
MaiMate 不會說「買 X」「賣 Y」「保證獲利」。

### 四層（任一層可獨立擋住）

| # | 層 | 位置 | 擋法 |
|---|---|---|---|
| 1 | 系統提示詞 | `backend/agent/loop.py:20` | 明訂「永不主動建議買賣特定標的」 |
| 2 | 後端正則 | `guardrails.py:8-13` `_ADVICE_PATTERNS` | 擋「建議買進/賣出」「一定會漲/跌」「保證獲利」句式 |
| 3 | 後端執行點 | `check_output()` `guardrails.py:79-100`，呼叫於 `handlers/chat.py:32-34` | 命中即**整段換掉**為 `SAFE_FALLBACK`（L103-106），不是遮字 |
| 4 | 前端 | `frontend/chat-core.js:26-31` FORBIDDEN 字典 | 後端萬一漏了，畫面這關再擋 |
| （5） | Bedrock Guardrails | `loop.py:109-115` | 設 `GUARDRAIL_ID` 即掛載，與上述疊加。**目前未建，見 §5** |

第 3 層的「整段換掉」是刻意的：部分遮蔽會留下半句話，使用者容易腦補成建議。

### 誤判防護（這條容易被忽略）

`_SAFETY_CONTEXT`（`guardrails.py:24-29`）把防詐教育語境排除在攔截之外。

原因：反詐騙內容**本來就必須出現**「保證獲利」「穩賺不賠」這些詞——那是在教人辨識詐騙話術。
沒有這個排除，護欄會把自家的反詐功能擋掉，而且失敗方式是靜默的（使用者只會覺得 AI 答非所問）。

**護欄設計不只要問「擋不擋得住壞的」，也要問「會不會擋掉好的」。**

## 3. 不碰保管與提領

| 主張 | 實作 |
|---|---|
| 資產全程留在 MAX，MaiMate 不經手 | 系統無任何錢包／代管邏輯；`max_private.py` 只做查詢與下單 |
| API 權限只開「讀取＋交易」，**不開提領** | 金鑰權限設定，見 `docs/DEPLOY.md` §2 與 `CAPTAIN_TODO.md` Part 2-1 C |
| 金鑰不進版控 | `infra/template.yaml:79-80` 註解說明刻意不宣告；部署後由主控台／Secrets Manager 注入 |

> 「不開提領」這條的證據是**權限設定截圖**，不是程式碼——程式碼無法證明自己沒有某個權限。
> 這也是為什麼交付清單把那張截圖列為必交項。

### 個資

輸入在進模型前先去識別化：`scrub_input()`（`guardrails.py:73-76`，正則於 L66-70），
掃身分證、手機、長數字串，呼叫點 `handlers/chat.py:19-22`。

## 4. 可問責：全程留痕

`audit.py:27-41` 的 `log()` 以 DynamoDB `list_append` 寫入，**append-only**——寫進去的不能改。

| 事件型別 | 埋點 | 意義 |
|---|---|---|
| `tool_call` | `loop.py:142` | AI 查了什麼 |
| `draft_created` | `tools.py:226` | 產生了哪張確認卡 |
| `user_confirmed` | `order.py:54` | 人在什麼時候按了確認 |
| `user_cancelled` | `order.py:45` | 人取消了 |
| `expired` | `order.py:52` | 憑證過期未執行 |
| `executed` | `order.py:58` | 實際成交 |

這串透過 `GET /audit` 回給前端的決策軌跡面板——**使用者自己看得到 AI 做了什麼**。
可問責不是「出事後查得到」，是「當下就看得到」。

## 6. 金管會「金融業運用 AI 指引」六原則對照

> 對照為工程自查，非法律意見；正式適用性須由法遵確認。

| 原則 | 我們的對應 | 證據 |
|---|---|---|
| **建立治理及問責機制** | 決策全程 append-only 留痕，使用者端可見 | `audit.py:27-41`；六種事件見 §4 |
| **重視公平性及以人為本** | 每一筆交易由人按下確認；AI 只提供選項不做決定；三種呈現風格只改密度、**不改數字** | `CONFIRM_TTL_SEC=60`（`tools.py:19`）；`order.py:25,29` |
| **保護隱私及客戶權益** | 入模型前去識別化；資產不經手；API 權限不含提領 | `scrub_input()` `guardrails.py:73-76` |
| **確保系統穩健性與安全** | 任一 API 掛掉自動降級為離線 mock 並**明示標示**；斷網不假造行情 | `app.js:170, 203, 366`；反向斷言於 `scripts/smoke_frontend.js` |
| **落實透明性與可解釋性** | 每個數字都附 evidence；數字與證據不符時整段換成安全模板 | 前端一致性檢查 `chat-core.js`；決策軌跡面板 |
| **促進普惠金融與永續發展** | 目標對象是散戶的行為偏誤，不是高頻交易者；模型分層控制單次成本 | `pick_model()` `loop.py:60-67` |

### 「以人為本」在這個產品裡的具體長相

不是 slogan。三種呈現風格（陪伴／簡潔／分析）只改**說法的密度**，
**數字一個都不會變**——因為數字是程式算的，LLM 只負責把它講成人話。
使用者換風格不會換到不同的事實。
